# 秒杀系统设计全链路：从前端挡流到 Redis 原子扣库存

秒杀系统的矛盾就一句话：海量瞬时请求，撞上极度有限的资源。99% 的流量在一秒内涌入，十秒后全部散去。平时 QPS 几百上千，秒杀瞬间飙到几十万甚至上百万；库存只有一千台，却有百万人来抢。

所有设计，全是在解决这一个冲突。本文按「前端 → 网关 → 业务 → 数据」四层拆解全链路，重点讲 MQ 削峰和 Redis Lua 原子扣库存的防超卖方案。

## 全链路架构

```text
前端层（挡掉 30%-40% 无效流量）
  ↓
网关层（限流 + 风控）
  ↓
业务层（MQ 削峰 + Redis 原子扣库存）
  ↓
数据层（Redis Cluster + MySQL 异步落库）
```

每一层只做一件事：前端挡无效流量，网关控节奏，业务层削峰扣库存，数据层保证最终一致。

## 第一层：前端挡流

前端主要做这几件事：

- **按钮置灰 + 倒计时**：防脚本自动狂点，减少无效请求
- **静态资源走 CDN**：图片、CSS、JS 不进源站，防带宽被打满
- **动态 URL**：秒杀开始前才下发带 token 的真实地址，防提前蹲点

这几招能挡掉至少 30%-40% 的无效流量。这层不碰业务逻辑，成本最低，收益却最先见效。

## 第二层：网关限流与风控

限流是进入系统后的第一道闸门。三种常见策略：

- **固定窗口计数器**：Redis `incr`，每秒上限 N。实现最简单，但有临界点突刺——0.9 秒和 1.1 秒两波请求叠加，瞬间击穿上限
- **滑动窗口**：Redis zset 细分时间片，比固定窗口精确，实现稍复杂
- **令牌桶（最常用）**：固定速率放令牌，请求领令牌，允许突发流量，代价是要维护桶状态

面试首选令牌桶，再讲清楚它与滑动窗口的区别：令牌桶允许突发，滑动窗口不允许。

网关层还应做简单风控：同一 IP 或用户 ID 短时间大量请求，直接拉黑。用 Redis set 或布隆过滤器，几毫秒出结果。

## 第三层：业务层——MQ 削峰 + 原子扣库存

请求进入业务层后不直接处理，先扔进 MQ 排队。业务系统能处理 5000 QPS，网关放进来了 10000，MQ 把多出的 5000 吃掉。用户看到的是「正在排队，前面还有 xxxx 位」。

**防超卖：Redis Lua 原子扣减 + MySQL 乐观锁**

直接在 MySQL 里 `UPDATE stock SET stock = stock - 1` 是致命错误：InnoDB 行锁会把数据库干废。正确方案是两层保险，先 Redis 后 MySQL。

Redis 侧用 Lua 脚本原子扣减：

```lua
local stock = redis.call('decr', KEYS[1])
if stock >= 0 then
    return 1        -- 扣减成功
else
    redis.call('incr', KEYS[1])  -- 补回库存
    return 0        -- 库存不足
end
```

关键点：不要先 `get` 再 `decr`，两步之间可能插进其他请求。直接用 `decr` 的返回结果判断，再用 Lua 把整段逻辑包成原子操作。

MySQL 侧用乐观锁兜底：

```sql
UPDATE stock SET stock = stock - 1
WHERE id = xxx AND stock >= 1
```

`affected rows == 0` 说明库存已空，回滚。Redis 挡掉绝大多数流量，MySQL 只做异步落库，两层保险。

扣库存全流程：

```text
请求 → MQ 排队 → Redis Lua decr
                  ├─ >= 0 → 异步写 MySQL（乐观锁）→ 下单成功
                  └─ < 0  → 返回「已抢光」
```

## 第四层：数据层

单机 Redis 的 QPS 上限约 10 万，扛不住秒杀。秒杀读多写少，扩容方向有两个：

- **Redis Cluster**：按商品 ID 哈希分片，各节点分摊流量
- **读写分离**：主节点写，从节点读

## 容量规划：从 1 万到 100 万 QPS

| QPS 量级 | 架构 | 核心组件 |
|---|---|---|
| 1 万 | 单机 | Redis + MySQL + 令牌桶 |
| 10 万 | 集群 | Nginx 负载均衡 + Redis Cluster + MySQL 主从 + MQ |
| 100 万 | 分布式 | 多级缓存 + ES 读写分离 + 微服务拆分 + 异地多活 |

从 10 万到 100 万，有四个关键变化：

1. **多级缓存**：本地缓存（Caffeine/Guava）→ Redis → CDN 三级联动
2. **读写彻底分离**：ES 扛查询，MySQL 只做冷数据归档
3. **业务拆分**：秒杀独立微服务，与主站解耦
4. **异地多活**：就近接入，库存数据专线同步

思路就一句话：单机撑不住就集群，集群撑不住就拆分，拆分撑不住就异地。

## 缓存三兄弟

秒杀是典型的读多写少场景，缓存是命脉，三个经典故障必须会答：

**击穿**：单个热点 key 过期，瞬间大量请求打到 DB。解法：互斥锁，第一个请求拿锁查 DB 回填，后面的等着；或逻辑过期，热点数据不设过期时间，value 里存逻辑过期时间，异步线程定期刷新。

**穿透**：请求数据库里不存在的数据，每次都打穿缓存。解法：布隆过滤器，提前存好所有存在的 key；或缓存空值，查不到也往 Redis 塞 null，过期时间设短。

**雪崩**：大量 key 同时过期，或 Redis 宕机，请求像雪崩一样全砸到 DB。解法：给每个 key 的 TTL 加随机偏移（如 3600~4200 秒），配合多级缓存，Redis 自身用哨兵/集群保证高可用，再加熔断降级。

## 面试官在看什么

系统设计题没有标准答案，面试官看三件事：

1. **全链路视野**：能不能从前端讲到数据库，每个环节为什么这么做
2. **方案的弹性**：QPS 翻十倍百倍时，设计能不能跟着长
3. **自知代价**：知道 Redis 宕机怎么办、MQ 积压怎么办、热点商品把分片打满怎么办

好的系统设计者不是给一个完美的方案，而是能说清楚每个选择的代价。

## 小结

秒杀系统的骨架是四层递进：前端挡流、网关限流、业务层削峰扣库存、数据层保证最终一致。防超卖靠 Redis Lua 原子扣减扛住瞬时流量，MySQL 乐观锁兜底一致性。

这套设计真正的价值在取舍：每一层只解决一个问题，每引入一个组件都要清楚它的代价。能说清代价，才算真正理解高并发。
