# 容器内通、容器外不通：一次 Docker 网络排障实录

## 背景与现象

环境是 CentOS 7，应用通过 Docker 部署。现象很拧巴：容器内访问服务一切正常，出了容器、在宿主机上访问对应端口，却提示不通。

端口映射是配了的，启动命令如下：

```bash
docker run -itd --name demo -p 8091:8091 myapp:latest
```

`-p 8091:8091` 的含义：把宿主机 8091 端口的流量，转发到容器内的 8091 端口。

映射存在，容器内也通，宿主机却连不上。现象就是标题那八个字：容器内通、容器外不通。

## 定位：把范围缩到容器与宿主机之间

排障先做两个方向的验证，每个方向都先确认前提，再下结论。

第一个方向，容器内访问。容器内能访问，说明容器里的进程在正常监听 8091，应用本身、监听地址都没有问题。

第二个方向，宿主机访问。宿主机访问不到，说明流量没能从宿主机进入容器。端口映射的配置没有问题，问题出在流量的传递路径上。

确认映射存在也很简单：`docker ps` 的 PORTS 列会显示端口对应关系，一致即生效。

再想一层：`-p` 只是声明「宿主机 8091 要映射到容器 8091」，映射要真正落地，依赖 Docker 的网络组件。默认 bridge 网络下，容器与宿主机之间的通信走 docker0 网桥，转发由 iptables 规则完成。这两个环节任何一个异常，都会出现「映射配了但不通」的结果。

所以结论明确：容器与宿主机之间的网络通信出了问题。方向定了，处理手段就是修复这条链路。

## 机制：为什么「内通外不通」是关键信号

先看容器内的访问路径。容器内访问 8091，走的是容器自己的网络命名空间，流量直达本机进程，不经过网桥，也不经过宿主机。所以容器内通，只能证明进程活着，证明不了链路。容器有独立的网络命名空间，相当于一张与宿主机隔离的网卡视图，容器内看到的网络状态和宿主机看到的不是同一份，两个方向的验证是在两份视图里各做了一次，结果要合起来看。

再看宿主机到容器的路径。宿主机 8091 → iptables 转发规则 → docker0 网桥 → 虚拟网卡 → 容器内 8091。任何一段异常，宿主机都会表现为「端口不通」。

`-p` 的转发规则是 Docker 启动容器时写入 iptables 的：宿主机端口上的入站流量先被 NAT 规则重定向，再交给 docker0，最后送进容器。规则和网桥是绑定的，网桥一旦异常，规则即使还在，流量也走不通。这也是为什么重建网桥要连同重启 Docker 一起做：转发规则要由 Docker 重新生成。

返回路径也一样。容器发出响应 → 虚拟网卡 → docker0 → iptables 改写源地址 → 宿主机端口 → 访问方。这条回包链路同样依赖 docker0 和 iptables 规则，网桥异常时一样会断。

这个症状的价值在于：把故障范围从「应用」一路缩小到「容器与宿主机之间的网络」，排查对象只剩 docker0 和转发规则。

## 方案：重建 docker0 网桥

docker0 是 Docker 默认创建的虚拟网桥。容器启动时，Docker 为容器创建一对虚拟网卡，一端在容器里，一端挂在 docker0 上。容器与宿主机、容器与容器之间的默认通信都经过这张网桥。网桥状态异常，映射流量自然走不通，正好对应「容器内通、容器外不通」的现象。

处理方式是重建 docker0：

```bash
# 1. 停止 Docker 服务
systemctl stop docker

# 2. 停用 docker0 网桥
ip link set dev docker0 down

# 3. 删除 docker0 网桥
brctl delbr docker0

# 4. 重建 docker0 网桥
brctl addbr docker0

# 5. 给网桥分配 IP
ip addr add 172.16.10.1/24 dev docker0

# 6. 启用网桥
ip link set dev docker0 up

# 7. 重启 Docker 服务
systemctl restart docker
```

顺序有讲究：

- 先停 Docker 再动网桥。Docker 运行时会自己管理 docker0，服务不停止就删桥，两边会互相干扰。
- 删除前必须先把网桥 down 掉。`brctl delbr` 不接受仍在启用状态的网桥。
- 重建时给 docker0 分配了新的网段 `172.16.10.1/24`，替代原先的桥地址。
- 重建用的是 brctl 命令，先确认系统装了 bridge-utils 工具包。

重建就是换掉异常的网桥：删除后新建一张，分配地址，重启 Docker 时重新生成配套的转发规则。

验证方式与排查时一致：在宿主机上重新访问 8091 端口，能通即恢复。

重启后验证，宿主机上可以正常访问容器内的服务，问题解决。

这套操作针对默认 bridge 网络。容器如果挂在自定义网络或 host 网络上，链路结构不同，处理方式也不同，不要照搬。

## 踩坑：一个多余的 iptables 操作

最初的操作清单里，删除网桥之后还执行过一条命令：

```bash
iptables -t nat -F POSTROUTING
```

这条命令会清空 nat 表 POSTROUTING 链上的全部规则，包括 Docker 为容器出网写入的 MASQUERADE 规则。事后验证，不执行这一步，问题同样能解决。

两个教训：

- 事后验证，这步不必要。清空 nat 表 POSTROUTING 链会把 Docker 的 MASQUERADE 规则一并清掉，属于破坏性操作，能不动就不动。
- 从机制上也说得通：后面重启 Docker 时，Docker 会重新生成自己的网络规则，清空的临时效果会被覆盖。

## 小结

这个问题的典型症状：端口映射存在、容器内通、容器外不通。遇到这种组合，优先怀疑容器与宿主机之间的网络链路，也就是 docker0 网桥。

两条经验可以复用：

- 分方向验证。容器内测一次、宿主机测一次，两次结果就能把故障范围从「应用」压到「网络」。
- 映射存在不等于链路通。`-p` 只是声明，落地要靠网桥和转发规则，链路异常时的表现就是「配了也不通」。

重建 docker0 是恢复手段，不是根治手段。如果同样的现象反复出现，要继续追查网桥异常的根本原因，不能只靠重建兜底。
