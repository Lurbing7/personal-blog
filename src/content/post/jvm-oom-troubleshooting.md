# 线上 OOM 排查：jstat、堆参数与 HeapDump

某快消行业客户的运营支撑系统跑在生产环境，Java 8 + Spring Boot。某段时间线上服务开始反复报 `OutOfMemoryError: Java heap space`，重启后短暂恢复，过一阵又复现。接口变慢、告警刷屏，这是最典型的线上 JVM 故障场景。

这次排查没有停留在「重启了事」，而是整理成一套可复用的套路：现象 → jstat 观察 → 堆参数调整 → HeapDump 配置 → 事后分析。下面按这个顺序展开，机制与命令都是通用做法，换一个项目同样适用。

## 现象与第一反应

OOM 的现场往往是这样：进程还在，但响应越来越慢，随后抛 `java.lang.OutOfMemoryError: Java heap space`；重启后恢复，运行一段时间后再次出现。

第一反应不是急着调大堆，而是先确认几件事：

- 近期有没有发布过新版本，改动集中在哪里
- 进程是否真的还在，用 `jps` 或 `ps -ef | grep java` 拿到 PID
- 系统层面有没有异常：内存、磁盘、CPU

盲目调大 -Xmx 只是推迟下一次 OOM，不解决根因。调参之前，先要让问题变得可见。

## 用 jstat 观察各区占用与 GC 频率

jstat 是 JDK 自带的监控工具，不需要额外安装，适合线上快速取证。基本用法：

```bash
# 每 2 秒采样一次，持续观察
jstat -gc <pid> 2000
```

输出各列对应 JVM 堆的分代结构：S0/S1 是幸存区，E 是 Eden，O 是老年代；YGC/FGC 是 Minor GC 和 Full GC 的次数，YGCT/FGCT 是累计耗时。

JVM 采用分代回收：新对象先进入 Eden，Minor GC 后存活对象在幸存区之间复制，多次存活后晋升老年代；老年代空间不足触发 Full GC。理解这条晋升路径，才能读懂 jstat 的输出。

观察要点有两个，而且一定要连续采样看趋势，单次快照说明不了问题：

- 各区占用是否持续上涨，尤其老年代的 O 列。上涨且不回落，说明有对象长期无法回收
- Full GC 频率与耗时：FGC 增长越来越快、FGCT 占比越来越高，说明老年代接近饱和

一个典型信号：老年代稳步上涨，Full GC 越来越频繁，每次停顿越来越长。基本可以判断存在无法回收的对象——要么是内存泄漏，要么是某个缓存或集合被无限填充。

## 按服务器内存调整堆参数

确认堆配置不合理后，调整遵循一个原则：**堆上限要与服务器物理内存匹配**，同时给操作系统和其他进程留足余量。

通用做法分三步：

1. 先看服务器内存，用 `free -h` 确认物理内存大小
2. 结合服务实际占用确定 -Xmx 上限，而不是拍脑袋定值
3. 重启后继续用 jstat 观察，确认各区占用回到预期水位

另一个要点是 -Xms 与 -Xmx 对齐。默认情况下 JVM 从 -Xms 开始，按需向上扩展；运行期堆反复伸缩会带来性能抖动。把两者设为相同值，启动时一次分配到位，GC 行为更可预测，后续用工具对比也方便。

```bash
# 示例：初始堆与最大堆对齐
java -Xms4g -Xmx4g -jar app.jar
```

参数调整解决的是「内存够不够用」，让服务能撑住当前流量；但为什么会有那么多对象占住内存，参数本身回答不了。

## 提前配置 HeapDump

线上 OOM 往往难以复现，最怕的是出事时没有现场。HeapDump 就是留现场的机制：加上参数后，OOM 发生时 JVM 自动把堆内存快照落盘，不需要人工介入。

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump
```

两个参数配套使用：前者是开关，后者指定 dump 文件目录。

配置时注意两点：

- 目录要提前创建并确认写权限，否则参数不生效
- 堆转储文件体积接近堆大小，磁盘要预留空间；生产环境建议把 dump 目录放到独立磁盘

有了这份现场，事后分析才有依据。这也是这次排查里收获最大的一步：把「重启了事」变成「每次 OOM 都留下证据」。

## 用 MAT 分析现场

拿到 dump 文件后，用 MAT（Memory Analyzer Tool）打开分析，主要看两块：

- 支配树：找出占用堆最大的对象及持有链
- 可疑泄漏点：MAT 会自动标注疑似泄漏的引用路径

顺着持有链往下追，就是从 GC Roots 出发做可达性分析：哪些引用让对象一直可达、无法被回收。顺着引用路径通常能定位到具体代码位置——比如某个全局缓存只进不出，或者一次查询把明细数据全量加载进内存。

这类根因往往不在 JVM 参数，而在业务代码。参数和 dump 只是让问题可被看见，修代码才是终点。

运行期如果需要佐证当前堆配置与实际占用，可以配合 `jmap -heap <pid>` 查看；日常也可以把 jstat 输出接入监控体系，作为持续观测手段。

## 小结

一次线上 OOM，完整闭环是：现象确认 → jstat 观察各区与 GC 频率 → 按服务器内存调整 -Xmx、对齐 -Xms → 提前配置 HeapDump → MAT 分析根因。

三个要点值得沉淀：

- 观察先于调整：先让问题可见，再动手改参数
- 参数匹配硬件：堆上限对服务器内存留余量，-Xms 与 -Xmx 对齐
- 现场必须提前留：HeapDump 配置要放在故障之前，而不是之后

这次排查最大的改变是心态：OOM 不是玄学，而是一条有固定流程的排查链路。把工具用熟、把流程固化，下次再遇到，就是按图索骥。
