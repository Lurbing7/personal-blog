# LLM 应用生产化：Token 成本治理与可观测性/容错设计

## 为什么需要治理

LLM 应用从 Demo 走向生产，最先暴露的是两件事：成本和稳定性。Token 单价看似很低，但未优化的 Agent 循环、冗余调用和长上下文会迅速消耗预算。

LLM 的输出是非确定性的。一次请求可能超时、可能返回错误格式、可能编造答案，需要比传统软件更完善的监控和容错机制。这两件事必须在设计阶段就做，不能上线后补救。

## 成本构成：先看清钱花在哪

总成本可以拆成一个公式：

```text
总成本 = ∑ (模型单价 × Token 消耗) + 基础设施 + API 调用费
```

LLM Token 费通常占 60-80%，是绝对大头。其余依次是基础设施 10-20%、Embedding 费 5-15%、向量库托管费 5-10%、第三方 API 5-15%。优化成本之前，先确认钱花在哪一层。

## Token 成本模型：输入便宜，输出贵

定价基本公式是输入单价 × 输入量 + 输出单价 × 输出量。输入通常比输出便宜 3-10 倍，所以输出 Token 对成本更敏感。

价格波动频繁，以下只是 2026 年的量级参考（$/1M tokens）：DeepSeek V3 输入约 0.27、输出约 1.10；DeepSeek R1 约 0.55 / 2.19；GPT-4o 约 2.50 / 10.00；Claude Sonnet 4 约 3.00 / 15.00。模型之间的价差可达一个数量级，选型本身就是最大的成本杠杆。实际以官方最新定价为准。

## 成本优化的四条路

**模型选型分级**。简单任务用小模型，复杂任务用大模型，节省潜力 40-60%；混合路由先让便宜模型尝试，不行再升级，可省 30-50%；非实时任务走更便宜的异步批量 API，可省约 50%。

**Token 优化**。精简 Prompt 模板可减少 30-50% Token；滑动窗口管理历史，避免上下文无限膨胀；用摘要替代完整历史可减少 70-90%；结构化输出代替自然语言格式，输出 Token 减少 20-40%。

**缓存**。四种缓存按场景选：LLM 响应缓存适合 FAQ 和固定查询；Embedding 缓存适合文档处理；检索缓存适合知识库问答；语义缓存按语义相似度命中，适合客服和搜索。

**Agent 成本控制**。反复循环的 Agent 是成本黑洞：思考 → 调用 → 观察 → 思考，10 次循环就是 10 倍成本。措施是限制最大迭代次数、缩短思考链（Token 减少 30-50%）、批量工具调用代替单步、失败快速降级避免重试浪费。

## 预算管理：分级控制

每月预算按预期请求量 × 平均每次成本 × 安全系数（1.5x）估算。消耗水位分级处理：低于 60% 正常运行；60-80% 预警并检查异常请求；80-95% 限流、降级为小模型；超过 95% 降级到免费模型或停服。

配套监控指标：日消耗增幅超过 50%（日环比）告警；失败/超时占比超过 5% 告警；单次请求成本超过平均 10 倍告警；Agent 平均循环超过 5 次告警。

## 可观测性：四层监控

监控从上到下分四层。用户体验层看响应时间、可用率、满意度；应用层看请求量、错误率、延迟分布；LLM 层看 Token 用量、首 Token 时间、输出质量和幻觉率；基础设施层看 CPU/GPU、内存、API 限速、网络延迟和存储。

## LLM 特有的指标

LLM 层有几个传统监控没有的指标。Token 消耗直接对应成本追踪；首 Token 时间对应用户体验；输出长度同时影响成本和质量；拒绝率反映安全和调优空间；幻觉率是质量核心指标；一致性衡量相同输入能否得到合理一致的输出；毒性/安全关乎合规。

## 可观测性工具怎么选

常用工具各有定位。LangSmith 适合 LangChain 生态，全链路追踪；LangFuse 开源可自托管，做成本追踪和评估；Weights & Biases 偏 ML 实验追踪和 Prompt 版本管理；Phoenix 开源，做性能和质量的监控；Helicone 轻量无侵入，是 LLM API 代理监控。也可以自研埋点，最灵活，但要自己开发维护。

## 容错设计：一条管线，六种策略

异常是常态，先认清常见异常。API 超时：重试 1-2 次后降级。速率限制：指数退避重试或排队。上下文超长：截断/压缩或分段处理。输出格式错误：重新生成或解析兜底。有害输出：内容过滤并拦截。幻觉回答：检索验证，必要时拒绝回答。

请求的容错管线可以这样组织：

```text
请求 → [限流器] → [重试器] → [超时控制] → [降级开关] → [结果]
                          ↓
                    [失败 → 熔断 → 备用路径]
```

六种策略各司其职：重试带指数退避，最多 3 次；超时为每一步设置独立超时，防止死等；熔断在连续失败 N 次后暂停调用；降级切换小模型、返回缓存或简单回复；限流控制请求速率，保护后端；隔离为不同模型/任务做线程池隔离。

## Agent 的异常处理

Agent 常见三类问题。陷入死循环：用最大迭代次数加超时兜底，必要时人类介入。工具调用失败：按重试 → 跳过 → 通知人类的顺序处理。产生错误决策：做决策验证，支持回滚，保留审计日志。

## 告警分级与上线清单

告警要分级并约定响应时间：错误率 > 5% 是 P0，即时响应；延迟 > 10s 是 P1，5 分钟处理；幻觉率 > 2% 是 P1，15 分钟处理；Token 日消耗超阈值是 P2，1 小时处理；API 限速触发是 P2，30 分钟处理。

上线前过一遍清单：是否配置了请求超时、指数退避重试、LLM 调用次数上限；是否监控 Token 消耗和成本；是否有异常输出的兜底和降级策略；是否有完整请求日志和告警通知。

## 小结

成本治理和可观测性是同一件事的两面：Token 消耗既是最大的成本项，也是最重要的监控指标。预算分级决定何时降级，容错管线决定降级之后系统还能不能正常响应。

把这套机制在写代码时一起设计进去，上线后就不会被账单和告警追着跑。
