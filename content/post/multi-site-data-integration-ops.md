# 多站点数据对接与同步运维：从点位配置到缺失排查

## 背景：20 多个站点，一套口径

在给某快消行业客户做数据平台期间，我负责一类典型的对接任务：把分布在各地、20 多个数据源站点的数据，持续同步到统一平台，再提供给下游分析和展示。

麻烦在于，站点不是一次性接完就结束。新站点要接入，老站点要切换，点位要增删，数据还会漏同步。两年左右的运维周期里，这类「数据源对接与同步」的排障和变更累计做了 50 多次，是运维工作里频率最高的一类。这篇文章记录其中的方法与经验：接入配置、点位变更、同步闭环、缺失排查。结论就一句话：**把变更做成固定流程，把排查做成固定 SQL**，多站点运维就不会失控。

## 数据源站点接入：先配点位，再建同步

每个站点的接入就两步：配好数据源，建好同步任务。

- **数据源配置**：登记站点的连接信息与调度方式，平台按配置去拉数据。
- **点位配置**：站点会采集哪些数据项，先登记成点位。点位是后面一切同步和检查的基准。

接入走「先小范围试点、再批量铺开」的节奏。试点站点跑通后，其余站点按同一套配置模板批量接入，减少逐个手配的出错面。

## 点位变更：新增、切换、删除

站点上线后，点位不是一成不变的。三类变更最常出现：

- **新增**：站点上了新采集项，补登记点位，必要时补历史数据。
- **切换**：采集来源变了，点位要改指向，同时核对切换前后的衔接。
- **删除**：采集项下线，点位要停用，避免空跑和脏数据。

变更量大时，手写 SQL 容易错。我的做法是先在 Excel 里整理变更清单，用 VLOOKUP/TEXTJOIN 之类的手段把字段拼成批量 insert 语句，核对无误后再执行。**批量变更的要点是生成与核对分离**：Excel 负责生成，人工负责核对。

## 同步闭环：备份 → 导出 → 执行 → 验证

所有数据源变更，都按同一个闭环执行，这是最值得复用的经验：

1. **备份**：先备份当前数据源配置，必要时在版本库建备份分支，出问题可整体回退。
2. **导出**：把现有点位导出成 Excel，和变更清单对比，确认要改的、要留的、要删的。
3. **执行**：执行对应的 SQL（update/insert），只做计划内的改动。
4. **验证**：对照导出结果验证变更生效，再确认同步任务正常产出。

漏做补做的教训很典型：某次变更只改了配置、没改对应的点位，同步结果对不上，回查流程才发现少了一步。此后每个变更都过一遍闭环，缺哪步一眼能看出来。

## 排查一：从 JSON 日志里定位同步状态

同步任务跑没跑、跑到哪一步，不能靠猜。平台把每次同步的详细过程写进日志，关键字段是 JSON 格式。

排查时用 SQL 的 JSON 取值运算符（`->>`）直接从日志里提取字段，按站点、时间、状态过滤，看某次同步的明细：

```sql
SELECT log_id, ts, log_data->>'site', log_data->>'status'
FROM sync_log
WHERE log_data->>'site' = '目标站点'
  AND ts >= '2026-09-01 00:00:00'
ORDER BY ts DESC;
```

`->>` 的优势是**不用把 JSON 展开成表，查询时直接取值**。嵌套字段、数组场景也能逐层取到，配合 WHERE 条件，可以快速锁定「哪个站点、哪一步、什么状态」。上面是示意写法，实际表名和字段以现场为准，记住思路即可：先把日志当普通表过滤，再按 JSON 字段下钻。

## 排查二：left join 找未同步记录

比同步失败更隐蔽的问题是「静默缺失」：任务显示成功，但某些记录根本没进到目标表。

这类问题用 left join 定位。以源表为主表，left join 目标表，凡是目标表补不上的，就是未同步记录：

```sql
SELECT s.id, s.site_id, s.updated_at
FROM source_table s
LEFT JOIN target_table t ON t.ref_id = s.id
WHERE t.id IS NULL
  AND s.site_id = '目标站点';
```

主表是「应该有的记录」，补不上的是「没同步过来的记录」。这个查询同时给出缺失列表和数量，既用于日常巡检，也用于修复后的复核——修完再跑一遍，结果应为空。

## 排查三：重复数据与配置被删

与缺失对应的是重复。统计结果不准，常是明细表里有重复记录。定位方式统一：

```sql
SELECT year, site_id, count(*)
FROM detail_table
GROUP BY year, site_id
HAVING count(*) > 1;
```

`HAVING count(*) > 1` 把有重复的分组挑出来，核对后清理，再重算结果。

另一类常见问题是配置被误删：标准配置缺失导致数据异常。排查时查出缺失的配置 ID，与 Excel 里的完整清单对比，补 insert 恢复。要点是**手里始终有一份导出的配置基线**，恢复就有据可依。

## 几点经验

- **流程比聪明重要**：固定闭环加固定 SQL，新接手的人也能照着做。
- **导出 Excel 是低成本的事实基线**：配置、点位、标准都定期导出，对比和恢复都靠它。
- **日志字段结构化**：同步日志用 JSON 存细节，排障时才能用 SQL 下钻。
- **验证是闭环的一部分**：变更完成不是结束，跑通验证才算数。

## 小结

多站点数据对接的难点不在接入本身，而在持续变化的维护。用「备份 → 导出 → 执行 → 验证」的闭环管住变更，用 JSON 字段解析和 left join 管住排查，两年里 50 多次的运维基本没有失控过。

这些方法不依赖具体业务：任何「多来源 → 统一库 → 下游消费」的架构都适用。技术细节会过时，流程和排查思路不会。
