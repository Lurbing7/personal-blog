# 一台服务器最多能撑多少条 TCP 连接？

## 这道题在问什么

面试里有一道高频容量题：一台服务器最多能撑多少条 TCP 连接？「最多」没有唯一答案，关键看从哪个层面回答。

这道题高频，是因为一层答案覆盖三个知识层：Linux 内核参数、TCP 四元组、内存估算。任何一个层面讲不透，答案都不完整。

拆开是三个层面：文件描述符限制、服务端资源上限、客户端四元组限制。下面逐层拆。

## 第一层：文件描述符

每条 TCP 连接在服务端都占一个文件描述符（fd）。fd 数量受三个参数限制：

- `fs.file-max`：系统级上限，root 不受此限制
- `soft/hard nofile`：进程级上限
- `fs.nr_open`：进程级上限，可针对用户设置

三个参数作用域不同：`fs.file-max` 管整个系统，`soft/hard nofile` 和 `fs.nr_open` 管进程。调参时要分清改的是哪一级。

三个参数又是耦合的。`fs.nr_open` 必须大于 hard nofile，否则用户无法登录。只调其中一个，是常见踩坑点。

改法也有讲究。用 `echo` 直接写入内核参数，改的是运行中的值，重启即失效，不推荐。要持久化，用 `/etc/sysctl.conf` 和 `/etc/security/limits.conf` 配合调整，两处配合可以调到 100 万 fd：

```text
/etc/sysctl.conf           # 内核级参数，如 fs.file-max
/etc/security/limits.conf  # 进程级 soft/hard nofile
# 两处配合，目标 100 万 fd
```

100 万 fd 这个量级，要和后面的内存估算配套看：fd 只是第一道门槛，撑不撑得住，还要看内存。

## 第二层：服务端资源

fd 调大了，连接数就能无限涨吗？不能。服务端还受 CPU 和内存限制。

先看理论上限。服务端固定监听一个 IP 和一个端口，连接靠对端的源 IP、源端口区分，上限是 2^32 × 2^16，约两百多万亿。其中 2^32 是对端 IP 的可能取值数，2^16 是对端端口的可能取值数。这个数字没有工程意义，只说明「理论上不是无上限」。

实际值取决于资源。一条空闲的 ESTABLISH 连接约占 3.3KB 内存，4GB 内存按这个数粗算，量级在百万以上，对应约 100 万条以上空闲连接。

注意「空闲」二字。一旦有真实数据收发，1000 条连接都可能吃力。开销大头是数据收发和业务处理，吃的是 CPU，不是连接本身占的内存。这正是空闲连接便宜、活跃连接昂贵的原因。

所以「能建立多少连接」和「能扛多少并发请求」是两回事。同样的连接数，业务不同，压力完全不同——这就是「抛开业务逻辑单纯谈并发没有意义」这句话的由来。

## 第三层：客户端四元组

能不能建立连接，还取决于客户端。TCP 连接靠四元组区分：源 IP、源端口、目标 IP、目标端口，四元组必须唯一，连接才能区分开。四元组里任何两个维度一旦固定，连接空间就由剩下两个维度决定。

一个固定 IP 的客户端，连同一个 IP、同一个端口的服务端，能变的只有源端口。端口是 16 位，最多约 65535 个，实际可用约 64000。这是单条链路上客户端的上限。

对比一下：服务端理论上限是 2^32 × 2^16，普通客户端却只有一个 IP，所以单条链路的瓶颈在客户端，不在服务端。

要突破这个上限，方向有两个：客户端多用几个 IP（×n），或服务端多监听几个端口（×m）。四元组任意一个维度变了，连接空间就随之扩大。

## 小结

完整回答分三层：fd 限制决定能不能建，服务端内存和 CPU 决定能建多少，客户端四元组决定单条链路的上限，三者层层递进、缺一不可。

最关键的一句：抛开业务逻辑单纯谈并发没有意义。连接数是容量估算的起点，不是终点。面试时把三层讲清楚，比背一个数字有用得多。
