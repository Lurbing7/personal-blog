# 线上性能排查三板斧：vmstat / iostat / perf + Arthas

## 背景：卡顿从哪里查起

线上服务一卡，第一反应是看 top。但 top 只能告诉你负载高不高，回答不了「为什么高」。CPU 烧满和磁盘写满，现象都是负载飙升，处理方式完全不同。

排查的关键是先分清方向：CPU 饱和还是 I/O 阻塞，持续问题还是偶发问题。方向错了，后面所有动作都是白费。

排查顺序是：vmstat 看全局方向，iostat 钉住磁盘，perf 抓偶发问题，Java 应用再用 Arthas 落到线程级。多数线上性能问题都能走到根因。

## 第一板斧：vmstat 看全局方向

vmstat 每秒刷新，一屏给出进程、内存、I/O、CPU 的综合状态：

```bash
vmstat 1
```

重点看四个字段：

- `r`：运行队列长度，等待 CPU 的进程数
- `b`：阻塞进程数，进程在等 I/O 时进阻塞
- `wa`：CPU 等待 I/O 的时间百分比，过高说明 I/O 是瓶颈
- `si/so`：交换分区换入/换出，非零可能内存不足

方向怎么判：wa 高、b 高，往 I/O 查；wa 低、us 接近 100%，往 CPU 查。这一步决定后面用什么工具。

配合 uptime 看平均负载：1 分钟、5 分钟、15 分钟三个值，持续高于 CPU 核心数的 75% 需要关注。dmesg | tail 看内核最新消息，OOM、磁盘错误常常先在这里露出痕迹。

同级别的工具按需补位：mpstat -P ALL 看每个 CPU 核心的利用率，判断负载是否均衡；pidstat 看单个进程的资源消耗；free -m 看内存，重点是 available 字段和交换空间使用量。

## 第二板斧：iostat 钉住磁盘

方向指向 I/O 后，用 iostat 看具体是哪块盘、等在哪里：

```bash
iostat -xz 1
```

关键指标：

- `%util`：设备利用率，持续大于 80% 可能是瓶颈
- `await`：I/O 请求平均等待时间，过长说明设备响应慢
- `avgqu-sz`：平均队列长度

写盘压力大的时候，%util 会顶到 100%，w_await 飙得极高。

这里有个容易误判的点：wa 高不一定是磁盘。网络 I/O 同样表现为等待，先用 nload（或 sar -n DEV 1）看网卡流量，排除网络再下结论，否则会查错方向。

## 第三板斧：perf 抓偶发问题

持续型问题好办，抓一段时间看统计就行。偶发问题麻烦：卡顿几秒就结束，vmstat、iostat 的瞬时状态根本来不及看。

常规工具难以捕捉瞬间状态，这时用 perf 做系统级采样：

```bash
sudo perf record -F 99 -a -g
sudo perf report
```

采样频率特意用 99Hz 而不是 100Hz：如果与系统周期任务同步，采样结果会系统性偏向某个周期，结论失真。perf report 给出函数级的 CPU 消耗分布，直接定位到问题进程和线程。

## 第四步：Arthas 落到 Java 线程

perf 找到进程后，如果是个 Java 应用，还要知道具体哪段代码在烧 CPU。Arthas 的 thread 命令列出线程并打印堆栈，卡在哪个方法上一目了然。

典型画面：top 里用户态 CPU 接近 100%，mpstat 确认各核心负载均衡，不是单核热点，Arthas thread 一抓，堆栈指向一个正在做密集数学计算的死循环线程。

## 三个实战场景

### 场景一：延迟升高，I/O 瓶颈

现象是系统卡顿、操作响应慢。top 一看 CPU 使用率不高但负载高——CPU 没满负载却高，多半是进程在等 I/O。

vmstat 确认 b 值高、wa 值很高，大量进程因等待 I/O 阻塞。先用 nload 排除网络，再用 iostat 定位：磁盘 %util 持续 100%，w_await 极高。根源是大量连续的磁盘写操作。

### 场景二：持续卡顿，CPU 瓶颈

top 显示用户态 CPU 使用率接近 100%，负载超高。mpstat -P ALL 确认各核心负载均衡。Arthas thread 定位到消耗 CPU 的线程和堆栈，根源是一个执行密集数学计算的死循环线程。

### 场景三：偶发卡顿，瞬时 CPU 飙升

系统间歇性、短暂卡顿，常规工具难以捕捉瞬间状态。perf 采样分析后，报告指向一个周期性触发的 CPU 密集计算任务。

## 排查要点与最佳实践

四个排查要点：

1. 快速定位：先看整体资源使用情况，再深入具体指标
2. 工具组合：不同工具各有侧重，需结合使用
3. 时间维度：偶发问题必须使用采样工具
4. 应用层面：定位到进程后，结合应用日志和代码分析

日常运维再补五条：系统正常时建立指标基线，便于对比；定期巡检，设置定时任务监控关键指标；结合应用日志和系统日志综合分析；资源使用率避免长期接近 100%；对关键指标设置阈值告警。

## 小结

卡顿排查的顺序是先定方向、再定位、最后落到代码。vmstat 判方向，iostat 定磁盘，perf 抓偶发，Arthas 落到 Java 线程。这几个工具过一遍，多数线上性能问题都能走到根因。
