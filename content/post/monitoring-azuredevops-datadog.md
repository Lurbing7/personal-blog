# 生产监控实战：从 CPU 曲线定位热点到用户行为回放

## 背景：生产环境的三种「查不出」问题

我在某快消行业客户的生产环境维护一个数据管理平台，线上系统托管在客户环境，日常排障靠监控平台和 CI/CD 流水线。团队没有专职运维，指标、日志、链路的排查链路都要自己打通。

线上问题大致分三类：第一类看得见指标但找不到根因，比如 CPU 突然升高；第二类复现不了，用户说没操作过，但数据就是不对；第三类根本到不了线上，构建阶段就失败了。三类问题对应三条排查路径，我逐一展开。

## 场景一：从 CPU 曲线定位热点接口

排查 CPU 高占用，第一步不是看代码，而是看曲线。Azure DevOps 的监控页面提供 CPU 占用率随时间变化的折线图，这是定位问题的第一现场。

做法分三步：先看曲线确认高 CPU 的时段，再把时间窗口和业务时间对齐，最后落到该时段对应的热点接口或业务操作上。曲线回答「什么时候、哪个方向」的问题，下钻才回答「具体是哪个接口」。

下钻一般分两层。第一层看应用层，把高 CPU 时段内的慢请求、报错请求筛出来，结合日志和链路追踪确认热点接口。如果服务接了 APM，直接看请求的端到端延迟和错误堆栈，Java 服务接 Datadog APM 只需在启动参数加 javaagent：

```java
java -javaagent:dd-java-agent.jar \
     -Ddd.service=my-app \
     -Ddd.env=production \
     -Ddd.version=1.0.0 \
     -jar my-app.jar
```

第二层看 JVM 层，配合 jstat 观察 GC 与堆使用，必要时用 jmap 抓 HeapDump 分析对象占用。多数热点问题在应用层就能定位，JVM 层工具用于确认内存与 GC 类原因。

这条路径的关键不是某个工具，而是时间对齐：CPU 曲线、日志、链路必须能按同一时间轴对照。这也是选择统一监控平台的原因——指标、日志、链路在同一界面，从一条曲线跳到当时的日志和 Trace，排查效率高很多。

## 场景二：用 Session Replay 回放用户操作

有些 bug 复现不了，问题不在代码，而在「用户到底做了什么」。日志记的是服务端视角，用户在前端的操作路径是黑盒，这类问题靠日志很难还原。

Datadog 的 Session Replay 补上这个缺口：用户操作时自动录屏。需要定位 bug 成因时，回放录屏确认用户的具体操作路径，辅助复现。两种场景最有用：用户不承认某个操作，回放直接确认事实；bug 偶发，回放能看到触发问题的准确操作序列。

机制上，Datadog 把指标、日志、链路三类数据统一采集到一个平台，Session Replay 补上用户侧行为数据这一环，与后端日志、链路串起来，才能拼出一次问题的完整画面。Agent 以轻量进程部署在每台机器上，资源占用小（通常 2-5% CPU、约 50 MB 内存），生产环境常驻可以接受。

使用上有一条边界：录屏涉及用户行为数据，只应用于排障场景，采集范围与保留策略要按合规要求控制。工具能做什么，和使用的边界是两回事。

## 场景三：CI 构建失败，卡在单测阶段

CI 阶段的问题最好查，一切都在流水线里。项目的 CI/CD 流水线在 Maven package 阶段会执行单元测试，单测失败直接导致构建失败。

排查路径固定：在 Azure DevOps 打开失败的那次运行，从 console 页面找到失败的测试用例和堆栈，修复后重新触发流水线。单测作为门禁，把问题拦在构建阶段，坏代码不会走到部署环节。「不通过不部署」是 CI 的底线。

这个场景的价值不在排查技巧，而在门禁设计：构建产物统一版本、可追溯，失败记录留在流水线里可随时回看，比线上出了事再翻日志省力得多。

## 方法论的沉淀

三个场景背后是同一套方法：

| 场景 | 关键手段 | 要解决的问题 |
|---|---|---|
| CPU 热点 | 曲线 + 日志/链路 + JVM 工具 | 指标异常找不到根因 |
| 操作复现 | Session Replay 回放 | 用户行为不可见 |
| 构建失败 | 流水线 console + 单测门禁 | 坏代码进入部署 |

还有两条工程习惯，日常运维里更常用。

第一，运维操作必须可回滚。数据修正类操作在运维里占比最高，一律先备份再执行，保留更新前后的对比和执行的 SQL，出问题能恢复到操作前。这个习惯比任何监控工具都重要。

第二，监控先于告警。没有专职运维的团队，优先选开箱即用、指标日志链路一体的平台；告警规则少而准，不要多而乱，否则告警疲劳会把真正的问题淹没。

## 小结

从 CPU 曲线定位热点接口，到 Session Replay 回放用户操作，再到 CI 单测失败排查，三条路径覆盖「指标异常、行为不可见、上线前失败」三类典型问题。

共同的方法是让问题可观测、可复现、可追溯。工具只是载体——Azure DevOps 提供流水线与监控曲线，Datadog 提供统一采集与录屏，真正起作用的是把时间轴对齐、把数据串起来的排查思路。
