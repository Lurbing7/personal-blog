# 我把 Obsidian 变成了会自生长的第二大脑：AI Agent + Git 闭环

## 为什么做这个项目

用 [Obsidian](https://obsidian.md) 记笔记容易，难的是让笔记体系持续生长。笔记越多，问题越多：分类、元数据、双链全靠手动、补写和回忆，过时内容没人管。整理变成了另一份全职工作，笔记只是堆积，不能变成行动。

目标很直接：把 Obsidian、AI Agent 和 Git 组合成可持续演化的个人 AI 知识库——Obsidian 管输入，AI 管整理和生长，Git 管版本沉淀。

## 三件套的分工

- **Obsidian**：写作入口，捕获想法、学习笔记、项目复盘和资料摘录，也是人的驾驶舱。
- **AI Agent**：整理引擎，负责分类、拆分、合并、补元数据、补双链、编译 wiki、生成报告。
- **Git**：版本系统，记录每次演化，保留回滚空间和 AI 协作痕迹。

知识库不是单纯的 Markdown 文件夹，而是一个半自动的学习系统。

## 目录模型：先立规矩，再谈生长

第一版用 `raw/` 目录模型，数字前缀表达分类：`00-inbox/` 临时收集，`01-languages/` 到 `08-interviews/` 按主题分类，另有 `10-ai/`、`11-网站搭建/`、`98-归档/`、`99-personal/`。

这一版后来被整体替换。当前模型按生命周期划分：`inbox/` 输入、`domain/` 可复用知识、`projects/` 实践、`assets/` 附件、`private/` 敏感区、`.archive/` 归档、`.wiki/` 编译产物。

输入采用混合模式：临时资料、网页摘录、AI 对话、灵感先进 `inbox/`；归属明确的正式笔记直接写入正式目录。Inbox 默认不编译进 wiki，整理定稿后才进入。

## 自生长闭环

系统靠一条流水线运转：

```text
Obsidian 捕获
→ inbox 临时收集
→ AI 分类 / 拆分 / 合并 / 补元数据
→ 移入正式目录
→ AI 补双链 / 概念链接
→ 编译 wiki
→ 更新搜索索引
→ 健康检查 / 缺口检测 / 新鲜度检查
→ 生成复习队列
→ Git 提交归档
```

六类 Loop 各司其职：Capture 收集，Organize 分类整理，Compile 把 `domain/` 编译成 `.wiki/`，Action 输出今日行动和任务队列，Review 复盘沉淀，Radar 筛选外部信息。每类 Loop 都要有明确输入输出和停止条件；AI 写完文档不算完成，必须有验证结果。

## AI 能做什么，不能做什么

AI 对普通知识目录可以偏激进：分类、移动、拆分、合并、补 `maturity / created / updated`、补双链、编译 wiki、更新搜索索引、检查知识缺口和健康度、更新复习队列。

但有一条红线：`private/`。简历、账号密码、个人规划、书签等含隐私、密钥的内容，AI 不自动删除、不合并、不编译进 wiki，涉及个人内容先询问用户。

权限模型落成硬规则：`inbox/` 可整理可移动，`domain/` 可编辑合并，`private/` 修改前必须询问，`.wiki/` 只能由编译流程生成，`.obsidian/workspace.json` 不进 Git。

## 踩过的坑：让 AI 干活，先学会踩刹车

第一个坑是第一版目录设计被推翻。`raw/` 模型后来整套换成生命周期模型，只留作历史记录。教训：目录结构是活的，先跑通最小闭环再收口，别追求一步到位。

第二个坑是自生长容易变成自我膨胀。于是加了输出限制：每个 Loop 最多 3 个行动建议，技术雷达最多 3-5 条，每周最多新增 5 个 todo，任务队列超 10 个先清理再新增。

第三个坑是 AI 越权。工作台第一屏有今日行动、AI 建议、Inbox 状态和可执行任务，但 AI 只能更新带 `AI-UPDATE` 标记的区域。增强前先回答五个问题：是否服务现实主线、是否减少负担、能否转化为行动、是否有明确输入输出和停止条件、是否会让系统变复杂。两个以上答不清楚，就不做。

重复内容直接合并、保留更完整的一版；过时内容移入 `.archive/`；低价值临时内容可删除，但要写进最近整理摘要说明。

## 小结

这个项目验证了一件事：知识库的「自生长」不是让 AI 无限整理，而是在明确边界下让 AI 持续完成低价值维护，把知识变成行动。Obsidian 管输入，Agent 管生长，Git 管沉淀，边界管失控。

自生长的对象是用户能力，不是文档数量。每轮从现实问题开始，到可验证的结果结束；没有停止条件的增长，不进入执行。
