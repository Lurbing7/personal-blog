# 生产环境数据修正的标准动作：备份、留证、可回滚

## 背景：改一行数据，牵一发而动全身

在某快消行业客户的生产系统上，我先后完成约 180 次数据修正类运维：重复数据清理、账号合并、记录恢复、配置补录、数据源调整。单看每一次，都是"改几条数据"的小事；合在一起，就是在客户生产系统上直接动数据。

数据修正最怕的不是改错，而是改错之后回不去。线上数据没有撤销键，delete 一旦提交就无法恢复；update 写错条件，影响的是一整批记录。

两年做下来，我把每次修正都收敛成同一套标准动作：备份、核对、执行、留证、可回滚。这套动作不依赖特殊工具，靠的是流程纪律。

## 一次修正的标准闭环

任何一次数据修正，都按下面的闭环走，顺序不能乱：

| 步骤 | 动作 | 留证 |
|---|---|---|
| 备份 | 复制目标数据到备份表，核对行数 | 备份表、备份文件 |
| 核对 | 导出当前数据，与需求方确认影响范围 | 导出的 Excel |
| 执行 | 执行修复 SQL，只动确认过的记录 | 更新 SQL |
| 留证 | 执行后再导出一份数据 | before/after 两份数据 |
| 验证 | 确认修复结果与后续同步状态 | 验证记录 |

备份是第一步，也是唯一不能省略的一步。备份 SQL 的通用写法：

```sql
-- 修改前备份：把目标数据完整复制到备份表
CREATE TABLE backup_业务表_20260901 AS
SELECT * FROM 业务表 WHERE 影响范围条件;

-- 校验备份行数，与修改行数对上
SELECT COUNT(*) FROM backup_业务表_20260901;
```

备份表行数要和修改行数对得上，对不上就先停手查原因。

## 定位重复数据：HAVING count(*)>1

出现过一次典型的指标异常：指标值算出来不准，排查后发现是明细表存在重复记录，同一组维度组合出现多条，统计被放大。

定位手法是分组加 HAVING，把重复组合找出来：

```sql
SELECT 维度1, 维度2, 维度3, COUNT(*) AS cnt
FROM 业务表
GROUP BY 维度1, 维度2, 维度3
HAVING COUNT(*) > 1;
```

定位只是第一步。找到重复记录后，先导出 Excel 留证，再与需求方核对哪些是应保留的记录，确认后才删除多余行。删之前先 SELECT 出影响范围，而不是直接 DELETE。

同类问题还有报表数据不准：排查后发现是逻辑删除的数据仍被统计。这类问题的共同点是"数据在，但语义错了"，修复的关键是先确认哪一条才是对的。

## 批量修复：Excel 生成 SQL

数据修正经常不是改一条，而是一批：一批数据源点位调整、一批配置补录、一批账号合并。手工一条条写 insert 容易出错，还不好核对。

做法是把目标数据整理进 Excel，用 VLOOKUP、TEXTJOIN 之类的公式把字段拼成 SQL 片段，再拼成完整的 insert：

```text
-- Excel 公式示例：把 A、B、C 三列拼成 insert 的一行
="('"&A2&"', '"&B2&"', '"&C2&"'),"
```

生成后先在 Excel 里检查一遍，确认列对齐、值无遗漏，再统一执行。批量补录走同样的闭环：先查缺失项，再生成 SQL，最后验证。

查缺失最常用的是 left join 找未同步记录：

```sql
SELECT s.*
FROM 源表 s
LEFT JOIN 目标表 t ON s.唯一键 = t.唯一键
WHERE t.唯一键 IS NULL;
```

## 双环境脚本与留证习惯

涉及存储过程、脚本和配置的修改，统一准备 prod/qa 两套脚本，先在 qa 环境跑通验证，再上 prod。同一套逻辑在两个环境各跑一次，能提前暴露环境差异导致的问题。

留证是贯穿始终的习惯：

- 每次操作留下 before/after 两份数据，加上更新 SQL
- 备份文件和导出的 Excel 按日期命名归档
- 删除类操作先导出 Excel 让需求方标记要删的记录，不自己判断

这些证据平时用不上，一旦线上数据出了问题，可以完整回放操作过程。我遇到过不止一次：问题被质疑时，翻出当时的备份文件和执行记录，几分钟就能说清楚改了什么、为什么改。

数据填反是另一类典型：两条记录的值互相写反，需要交换回来。修正 SQL 不大，但稍不留神就把两边都改错，更要先备份、先留证。

## 几个要点

- 先备份再动手：delete/update 之前必须有备份，备份行数与源数据核对
- 影响范围先确认：DELETE 之前先 SELECT 看影响行数，宁可多核对一次
- 修复后验证同步：数据源同步类操作，修复后查同步日志和未同步记录
- 重复运维沉淀成脚本：同类操作固化成脚本，减少手误
- 生产改动走 Git 分支管理，关键发布留备份分支

## 小结

约 180 次数据修正沉淀下来的方法论，不外乎三件事：备份、留证、可回滚。

数据修正不是越快越好，而是越稳越好。每个动作都留下痕迹，出问题能回滚、能复盘，这才是生产环境数据修正该有的样子。
