# AI 上下文压缩实测：Headroom 的宣传数字与我的真实收益

## 背景：想给编码 Agent 省点 Token

用 AI 编码 Agent 干活，Token 成本和上下文爆满是绕不开的两个问题。长任务里，工具输出、日志、文件内容一路堆进上下文，窗口接近上限后回答质量下滑，费用也在涨。

Headroom 是一个开源的 AI Agent 上下文压缩层（[GitHub](https://github.com/headroomlabs-ai/headroom)）。它做的事情很简单：在提示词、工具输出和日志到达 LLM 之前，本地压缩一遍再发出去。官方宣传很诱人——代码搜索压缩 92%，号称压缩不损准确度。我按官方流程接入了 Codex 试了一个月，结论与宣传差距很大。

## 它怎么工作

Headroom 的流程可以概括为：

```text
你的 Agent / 应用 → Headroom（本地压缩） → LLM 提供商
                      ↓
                本地存储原始数据，LLM 可按需取回
```

核心是三个压缩器：SmartCrusher 处理工具调用产生的大量 JSON，保留结构和关键字段；CodeCompressor 做 AST 级代码压缩，支持 Python、JS、Go 等六种语言；Kompress-base 是在 HuggingFace 开源的文本压缩模型，专门在 Agent 对话轨迹上训练。

ContentRouter 按内容类型自动路由，CacheAligner 稳定发送前缀、提高缓存命中率。压缩是**可逆**的：原始数据完整留在本地，LLM 需要细节时调用 `headroom_retrieve` 工具取回。数据全程不离开机器，这是它对比托管压缩服务最核心的卖点。

## 官方宣传的数字

官方基准测试给的数字很漂亮：

| 工作场景 | 压缩前 | 压缩后 |
|---|---|---|
| 代码搜索（100 条结果） | 17,765 | 1,408 |
| SRE 事故调试 | 65,694 | 5,118 |
| GitHub Issue 分类 | 54,174 | 14,761 |
| 代码库探索 | 78,502 | 41,254 |

代码搜索和 SRE 调试都省了 92%。准确度基准同样好看：GSM8K 数学推理分毫不差，TruthfulQA 甚至微升。按代码搜索场景估算，日均 100 次、每月 20 个工作日，能省约 98 美元。

## 我的真实收益

我通过 `headroom wrap codex` 接入，让 Codex 的模型请求走本地代理。实测结果：

- 长任务实际压缩率约 0.5%，和宣传的 60%-95% 差了两个数量级
- 首次只读探针报告约 7.1% 的输入上下文压缩，同样远低于宣传值
- Codex 原生在上下文窗口接近满载时能自行压缩；接入 Headroom 后反而出现要求新开线程的情况

0.5% 意味着 Token 节省几乎可以忽略，却要多养一个代理进程，还要处理 session 隔离等问题。维护成本远高于收益。

## 差距为什么这么大

官方高压缩率来自特定负载：长日志、批量搜索、大规模代码探索。这类场景充满重复结构的 JSON 和日志，恰好是压缩器最擅长处理的。

我的日常是短任务、重复读取不多的会话，加上 Codex Desktop 自身的系统上下文和工具协议，收益只剩个位数。还有一个认知偏差要纠正：Headroom 报告的压缩量，不等于订阅配额按相同比例减少。

## 接入方式和安装坑

Headroom 有四种接入方式。库模式在代码里直接调 `compress()`；代理模式零改动，把任何 OpenAI 兼容客户端指向本地端口；包装模式一行命令包住 Agent；MCP 模式按需提供压缩工具。建议先用 MCP 模式验证效果，再考虑代理模式接管全部流量。

安装配置我踩了五个坑：

- npm 包只是 TypeScript 库，不带 CLI；CLI 在 Python 包里，要 `pip install "headroom-ai[all]"`
- pip 不在 PATH，或虚拟环境里没装 pip，改用 `python -m pip`，必要时先 `python -m ensurepip --upgrade`
- Python 3.14 装不上：Rust 核心经 PyO3 绑定，PyO3 0.22.6 最高支持 3.13，换 Python 3.10~3.13 或设置 ABI3 兼容变量
- CLI 装好不等于 Agent 会用，还要 `headroom mcp install` 注册
- `wrap codex` 会改 `~/.codex/config.toml` 写入独立 provider，Codex 按 provider 隔离线程历史——看着像 session 全没了，其实是列表切换，不是删除；接入前先备份配置

## 代理的生命周期坑

代理模式是「长期配置 + 短期进程」的组合：`config.toml` 里的 provider 配置会一直留着，代理进程关机就消失。Windows 重启后 Codex 仍指向本地 8787 端口，端口却没人在听，表现是发消息失败或 502。

最坑的是端口在监听不等于转发成功。实测里 `GET /v1/models` 返回 502，同一轮的 WebSocket 请求却正常，502 的精确根因最终没有确认。排查要先看端口，再看代理日志有没有入站记录。想继续用，就得每次开机手动起代理或做开机自启动；想省心，直接恢复配置备份，把 provider 切回默认。

## 小结

对以短任务为主的个人用法，Headroom 不值得装。我留了三个继续使用的条件：长任务跑完后 `headroom perf` 有稳定收益、任务质量和速度没下降、能接受 session 隔离和代理生命周期。三个条件不同时满足，就用 Agent 自带的压缩和更短、更聚焦的任务拆分。

宣传数字来自特定负载，个人收益必须自己实测。工具再好，也要先确认它解决的问题是不是你真正遇到的问题。
