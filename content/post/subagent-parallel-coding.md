# 用子代理并行拆解编码任务：四种编排模式与成本权衡

## 背景与问题

子代理（Sub-agent）是 Claude Code 通过 Task 工具派生的独立 AI 实例。每个子代理拥有独立的上下文窗口，主代理负责派发任务并汇总结果，适合把复杂任务拆开并行执行。

没有子代理时，跨多个文件的重构、多模块分析这类任务只能在主代理里串行处理：逐个文件读、逐个模块分析，前一步没完成，后一步就等着。任务越长，主代理上下文被占得越满，等待越久。子代理的思路是把它拆成互相独立的小任务同时开工，最后汇总。

## 什么任务值得拆

拆分的收益取决于任务是否互相独立：

- 修复单个文件里的 bug：直接让主代理改，不拆
- 跨多个文件的重构：每个文件一个子代理并行
- 代码审查：多个子代理并行审查不同维度
- 调研不相关的问题：同时搜索多个方向
- 多模块分析：每个模块一个子代理

依赖关系决定编排方式：没有依赖的拆开并行，有依赖的按顺序走，后者对应下面的模式二。

## 模式一：并行文件分析

多个文件互相独立时，每个文件派一个子代理，主代理最后汇总。

```text
主代理                 子代理
  │──→ sub-agent 1: 分析 UserController.java
  │──→ sub-agent 2: 分析 OrderService.java
  │──→ sub-agent 3: 分析 PaymentGateway.java
  │
  ←── 汇总三份分析结果
```

适用场景：代码审查、安全审计、技术债务评估。

## 模式二：分步重构

任务之间存在依赖时，按顺序执行，上一步的输出是下一步的上下文。

```text
主代理                   子代理
  │──→ sub-agent 1: 提取接口定义
  │
  │──→ sub-agent 2: 实现新接口（依赖 sub-agent 1 的输出）
  │
  │──→ sub-agent 3: 迁移旧调用方（依赖 sub-agent 2 的实现）
  │
  ←── 验证重构结果
```

适用场景：有依赖关系的多文件重构。

## 模式三：多维度审查

同一份代码从不同角度并行审查，一次拿到多份报告。

```text
主代理                             子代理
  │──→ sub-agent 1: 安全性审查（SQL 注入、XSS、认证绕过）
  │──→ sub-agent 2: 性能审查（N+1 查询、内存泄漏、缓存缺失）
  │──→ sub-agent 3: 可维护性审查（代码重复、命名、设计模式）
  │──→ sub-agent 4: 正确性审查（边界条件、并发问题、异常处理）
  │
  ←── 汇总四份审查报告
```

适用场景：PR 审查、上线前质量门禁。

## 模式四：调研—验证—输出

技术选型这类任务拆成调研、对比、验证三个阶段。

```text
主代理                             子代理
  │──→ sub-agent 1: 调研方案 A 的可行性和成本
  │──→ sub-agent 2: 调研方案 B 的可行性和成本
  │
  ←── 对比分析，推荐方案
  │
  │──→ sub-agent 3: 验证推荐方案的边界情况
  │
  ←── 输出最终方案文档
```

适用场景：技术选型、方案设计。

## 模型选择与成本权衡

子代理默认使用与主代理相同的模型，可通过环境变量指定轻量模型：

```json
{
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "claude-haiku-3-5-20241022"
  }
}
```

模型按任务的理解深度分三档：

| 任务类型 | 推荐模型 | 理由 |
|---|---|---|
| 文件扫描、批量替换 | Haiku | 简单任务，速度快、成本低 |
| 代码审查、测试生成 | Sonnet | 需要理解力，不需要深度推理 |
| 架构分析、安全审查 | Opus | 复杂推理，值得多花成本 |

成本上有两个数字最直观：Haiku 比 Sonnet 快 2-3 倍，成本低 5 倍。并行子代理数量不是越多越好，3-5 个最佳——更多子代理只增加总 token 消耗，收益递减。

中国大陆用户使用阿里云百炼时，子代理模型需要设置为百炼支持的模型名，比如 `qwen3.6-plus`，成本更低。

## 实战案例

两个典型的用法。

**批量修复 ESLint 错误**。主代理先派活："对 src/ 目录下每个有 ESLint 错误的文件，各派一个子代理修复"。具体策略：先用 Grep 找出所有有错误的文件，为每个文件派一个子代理，各自修复单个文件的错误，最后主代理运行 `npm run lint` 验证。

**多文件 API 改造**。把 UserController 从 REST 改为 GraphQL，涉及 Controller、Service、DTO 三层。按依赖拆分：子代理 1 扫描现有 REST 接口定义，列出所有需要迁移的端点；子代理 2 设计 GraphQL Schema；子代理 3 根据 Schema 改造 Service 层；子代理 4 改造 Controller 层为 GraphQL Resolver。主代理整合变更，验证编译通过。

## 踩过的坑与注意事项

- 子代理不共享上下文，每个子代理都需要接收完整的指令，指令给得越精简越好
- 子代理的输出越结构化（如 JSON 格式），主代理汇总效率越高
- 过多子代理同时运行会导致 token 消耗激增
- 子代理运行期间主代理处于等待状态，无法同时处理其他事情——并行省的是墙钟时间，不是主代理的投入

## 小结

子代理的核心理念是把一个大任务拆成互相独立的小任务并行执行，主代理只负责派发与汇总。四种模式覆盖了大多数场景：独立的拆开并行，有依赖的按顺序走，同一份代码多角度审查，选型类任务拆成调研、对比、验证。

成本权衡是唯一的反向约束：并行越快，token 消耗越大。用轻量模型处理简单任务、把并行数控制在 3-5 个、要求子代理输出结构化，是控制成本的三个基本动作。
